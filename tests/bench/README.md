# Сравнительный бенчмарк: Nano-Sparrow vs Caddy vs Nginx

Стенд на docker compose: четыре сервера с **одинаковыми эндпоинтами** гоняются под
wrk-нагрузкой из отдельного runner-контейнера, который параллельно снимает
CPU/RSS серверов (docker stats), умеет портить соединение (`tc netem`) и рисует
графики matplotlib. Nano-Sparrow собирается из репозитория, остальные — с Docker Hub.

## Одна команда для проверяющего

```bash
cd tests/bench
./run.sh
```

Скрипт сам: проверит docker, соберёт образы (если их нет), поднимет все
контейнеры, прогонит бенчмарк (WORKERS=1 и 3, демо-режим ~15-20 минут),
напечатает сводную таблицу на экран и снова снимает контейнеры.
Результаты и графики остаются в `results/`.

- `./run.sh --full` — полная матрица (по 15 с на сценарий, ~35-45 минут)
- `./run.sh --build` — только предварительная сборка образов (полезно на
  машине без интернета: собрать заранее, потом `./run.sh` работает офлайн)
- `./run.sh --down` — снять стенд без прогона
- `./run.sh --max-conns N` — лимит соединений в конфигах (sparrow
  `max_connections`, nginx `worker_connections`) для основной матрицы
- `./run.sh -- --workers 1 --duration 8 --no-sweep` — свои параметры
- Exit code 0 = успех: `./run.sh && echo PASS`
- Если нужен лог, используйте `./run.sh | tee log.txt`, а НЕ `./run.sh > log.txt`:
  docker из snap (CLI в `/snap/bin/docker`) при stdout в обычный файл молча теряет
  вывод и портит exit code — пайпы и терминал работают нормально.

Кроме сравнительной матрицы каждый прогон включает **research-фазу**:
для нескольких значений `max_connections` (по умолчанию
`5000 10000 15000 20000`, флаг `--conns-research "5000 20000"`) стенд
пересоздаётся с этим лимитом (workers=1) и снимается idle-память всех
контейнеров + один прогон `/status`. Показывает главное отличие sparrow:
память преаллоцируется под пул соединений и растёт линейно (10k → ~127 МБ),
остальные серверы аллоцируют по требованию и остаются плоскими. Итог —
`memory_conns.png` и блок «Память при max_connections» в сводке. Отключить:
`--no-research`.

## Фаза «чистый sparrow» (отдельный скрипт)

`run_only_sparrow.sh` — анализ производительности ТОЛЬКО Nano-Sparrow при
разных значениях `max_connections` (лимит задаётся в КОНФИГЕ sparrow:
`configs/sparrow/server.conf`/`server-tls.conf`, а не параметром wrk). nginx и
caddy останавливаются, гоняется полная матрица сценариев + badnet + sweep +
idle-память (workers=1) для каждого значения лимита.

```bash
./run_only_sparrow.sh                    # max_connections 1000 и 5000
./run_only_sparrow.sh --conns "1000 5000 10000"  # свои лимиты
./run_only_sparrow.sh --full             # полные длительности (15 с на сценарий)
./run_only_sparrow.sh --down             # снять стенд без прогона
```

Результаты — в отдельной папке `results-sparrow/` (`results.json`, `results.csv`,
`sparrow_only.png`, ASCII-сводка на экране) — сравнительный `./run.sh` и его
`results/` не трогаются. Флаги `--no-badnet`, `--no-sweep`, `--scenarios` и
прочие пробрасываются через `--`.

Что показывает фаза (демо-прогон, 6 с на сценарий, эта машина; формат rps / p99):

| Сценарий | max=1000 | max=5000 |
|---|---|---|
| `/status` (keep-alive) | **165 156** / 6.0 мс | 158 246 / 6.3 мс |
| `/status`, `Connection: close` | 5 423 / 26.2 мс | 5 318 / 27.6 мс |
| TLS `/status` | 98 391 / 128.1 мс¹ | **99 715** / 43.5 мс¹ |
| gzip `/static/mid.txt` (1.3 КБ) | 60 811 / 9.3 мс | 60 903 / 11.9 мс |
| `/static/small.txt` (86 Б) | 63 835 / 3.4 мс | 65 385 / 3.2 мс |
| `/static/big.bin` (10 МБ) | 1 072 / 33.5 мс | 1 082 / 32.7 мс |
| proxy GET `/api/ping` | 1 011² / 1 350 мс² | 1 071² / 1 300 мс² |
| badnet latency 50±10 мс | 631 / 73.8 мс | 629 / 74.1 мс |
| badnet jitter 20±15 мс | 1 536 / 53.4 мс | 1 525 / 54.8 мс |
| badnet loss 2% | 7 780 / 207.1 мс | 7 701 / 206.5 мс |
| idle anon RSS (http) | **13.1 МБ** | **63.8 МБ** |

в Python-бэкенд.

Потолок пула соединений виден в sweep-части: при `max_connections=1000` точка
`c=1024` помечена «потолок пула» — sparrow по конфигу отклоняет соединения сверх
лимита, wrk честно считает их ошибками, но сервер не падает (rps ~150k против
~157–161k на меньших конкарренси). Итог — `results-sparrow/sparrow_only.png`.

### Память vs max_connections: почему idle RSS растёт линейно

| max_connections | 1 000 | 5 000 | 10 000 | 15 000 | 20 000 |
|---|---|---|---|---|---|
| idle anon RSS (http), МБ | 13.1 | 63.8 | 126.8 | 190.0 | 210.7 |
| idle anon RSS (tls), МБ | 13.0 | 63.6 | 126.8 | 190.0 | 210.8 |

Корреляция прямая и строго линейная (~12.6 МБ на 1000 слотов) — потому что вся
память под соединения выделяется **один раз при старте**, до любой нагрузки:

- `connection_buffers_ = new char[max_connections × buffer_size × 2]` —
  единый блок rx/tx-буферов по 8 КБ на слот (src/server.cpp:131-135);
- пулы слотов `Connection` (с mbedtls-контекстом) и `UpstreamConnection`
  (include/memory_pool.hpp: конструктор аллоцирует всё сразу);
- кольцо io_uring: `entries = max(4096, min(2×max_connections, 32768))`
  (src/server.cpp:314-317) — кап 32768, иначе ядро отвечает EINVAL;
- регистрация tx-буферов для SEND_ZC: `min(max_connections, 16384)`
  (src/server.cpp:365) — лимит ядра IORING_MAX_REG_BUFFERS.

Отсюда же флэттен между 15k и 20k: вместо ожидаемых ~253 МБ измерено 210.7 —
слоты сверх 16 384 регистрируемых буферов не «материализуют» свои страницы при
idle, поэтому последние 3.6k слотов почти не видны в RSS. Практический вывод:
нужный лимит нужно задавать осознанно — это предоплата за zero-alloc на горячем
пути (при старте нет ни одной рантайм-аллокации под нагрузкой).

### Почему p99 такой

p99 в этой фазе практически **не зависит от `max_connections`** (колонки 1000 и
5000 совпадают) — он определяется четырьмя независимыми источниками:

1. **Насыщение одного воркера** (`/status` p99 6.0–6.3 мс при p50 0.13–0.14):
   165k rps на 1 ядре — p99 это хвост очереди кольца io_uring и редкие задержки
   планировщика. Размер пула не влияет: слоты не переиспользуются, лимита по
   факту нет (c=64 << max).
2. **Путь установления соединения**: без keep-alive (5.4k rps) каждый запрос —
   это SYN→accept→запрос→close; p99 26–28 мс при p50 1.6–1.8 мс — стоимость
   accept-пути и переполнения accept-очереди. `static_small` (3.2–3.4 мс) и
   `static_big` (32.7–33.5 мс при p50 12.3 мс): трансфер 10 МБ, хвост —
   конкуренция за docker-bridge (~0.85 ГБ/с на соединение по p50, на p99 вдвое
   меньше), а не лимит сервера (в матрице при 10k пул был быстрее — 26.3 мс).
3. **Бэкенд**: proxy p50 41 мс (латентность Python-бэкенда) и p99 1.30–1.35 с —
   очередь/тормоза бэкенда под нагрузкой (GC, threading) — идентично при обоих
   лимитах и в сравнительной матрице. `proxy_post` (44.6 vs 396 мс) — чистый
   шум бэкенда: в матрице при max=10000 было 1430 мс.
4. **Сеть**: badnet целиком диктует netem — 74 мс (задержка 50 мс в одну сторону:
   RTT ~100 мс потолок), 53–55 мс (jitter 20±15), 207 мс (loss 2% — таймауты
   TCP-ретрайсов), и на всех серверах одинаково.

Исключение — **TLS**: p99 128 мс при max=1000 против 43.5 мс при max=5000, при
одинаковом p50 (0.23 мс). Это шумный хвост конкурентных рукопожатий на одном
воркере, а не следствие размера пула: в сравнительной матрице (max=10000) тот же
сценарий дал p99 99.3 мс — демо-прогон (6 с) недостаточно длинный, чтобы
стабилизировать 99-й процентиль TLS. Sweep-часть показывает вторую сторону
потолка пула: при c=1024 и max=1000 p99 **лучше** (33 мс), чем при max=5000
(60 мс) — отклонённые сверх лимита соединения не создают очереди на сервере.

Требования: Linux + docker с compose v2. Примечание: docker через snap может не
видеть пути вне `$HOME` (например `/tmp`) — держите бенчмарк в рабочей директории.

## Топология

```
           runner (wrk + docker CLI + NET_ADMIN)
              |  tc netem на eth0 (для сценариев "плохого соединения")
              v
   +----------+-----------+--------------+
   |  sparrow |  caddy    |  nginx       |
   |  :8080   |  :8080    |  :8080       |
   |  :8443   |  :8443    |  :8443       |
   +----------+-----------+--------------+
              |         все: /api/* -> backend:9090 (172.30.0.10)
              v
         backend (python http.server)
```

Хост-порты только для ручного запуска: HTTP `18080` (sparrow), `18082` (caddy),
`18083` (nginx); TLS `18443` (sparrow), `18445` (caddy), `18446` (nginx). **Runner
бьёт по внутренним DNS-именам** (`http://sparrow:8080`), иначе netem не действует.

## Одинаковые эндпоинты

| Путь | Что отдаёт | Кто реализует |
|---|---|---|
| `/status` | маленький JSON | sparrow: встроенный handler; caddy: `respond`; nginx: файл `status.json` |
| `/static/small.txt` (86 Б) | мелкий файл | sparrow: буферный путь; остальные: file_server/alias |
| `/static/mid.txt` (1.3 КБ) | gzip на лету (Accept-Encoding: gzip) | sparrow: gzip-статика; caddy: `encode`; nginx: `gzip on` |
| `/static/big.bin` (10 МБ) | несжимаемый raw | sparrow: zero-copy SEND_ZC; остальные: sendfile/чтение |
| `/api/*` | прокси на backend | все три (sparrow: стриминг с backpressure) |

Замечания о честности:

- **gzip**: все серверы сжимают только при `Accept-Encoding: gzip` (как в браузере).
  Сценарий `gzip_mid` шлёт этот заголовок, остальные — нет (сравниваются raw-пути).
  nginx/caddy не сжимают ответы меньше 20 Б (`gzip_min_length`/`minimum_length`),
  sparrow — меньше 150 Б (словарь gzip дороже тела).
- **`/status` у sparrow** — динамический JSON, у nginx — файл с диска; на
  пропускную способность не влияет (тело одинаково маленькое).
- **CPU%** — из `docker stats`, в процентах от ВСЕХ ядер хоста (100% = одно ядро).
  Для честного сравнения задержек не запускайте нагрузку на машине параллельно.

## Матрица сценариев (wrk -t4, 15 с, если не указано)

1. `status` — маленький JSON, keep-alive
2. `status_noka` — `Connection: close`
3. `tls_status` — HTTPS `/status`
4. `gzip_mid` — `/static/mid.txt` + `Accept-Encoding: gzip`
5. `static_small` — 86 Б файл
6. `static_big` — 10 МБ raw (zero-copy путь sparrow)
7. `proxy` — GET `/api/ping` → бэкенд
8. `proxy_post` — POST `/api/echo` с телом (стриминг аплоада)
9. badnet-серия — `/status` c=32: base / latency 50±10 мс / jitter 20±15 мс / loss 2%
10. sweep — rps от числа соединений 1/16/64/256/1024

## Плохое соединение (`tc netem`)

Runner имеет `NET_ADMIN` и накладывает netem на свой `eth0`:
`tc qdisc add dev eth0 root netem delay 50ms 10ms distribution normal` и т.д.
Портятся ВСЕ пакеты runner → серверы, поэтому сравниваются честно; соединения
серверов между собой (backend) не трогаются. netem снимается после каждого
сценария.

## Сравнение памяти

В сводке после rps/latency печатается таблица «ПАМЯТЬ, МБ» на каждый WORKERS
(строки — контейнеры; sparrow представлен двумя процессами: `sparrow http` и
`sparrow tls`), графики — `results/memory_<w>.png`:

Отдельно research-фаза рисует `results/memory_conns.png`: idle-память и rps
`/status` при разных `max_connections` (5k/10k/15k/20k) — видно, как sparrow
преаллоцирует пул соединений, а nginx/caddy остаются плоскими.

| Метрика | Что означает |
|---|---|
| `idle RSS` | анон-память процесса (без page cache) сразу после старта, **до** любой нагрузки |
| `idle usg` | то же + page cache + kernel (`memory.current`), т.е. «docker stats MemUsage» |
| `peak RSS` | максимум анон-памяти за все сценарии матрицы |
| `peak usg` | максимум общего usage за все сценарии |
| `peak cache` | максимум page cache (`file`-страницы: файловая статика) |

Как это снимается: `anon`/`file` берутся из `memory_stats.stats` Docker API
(`GET /containers/<name>/stats`, unix-сокет `docker.sock` из runner'а) — не из
`docker stats`, потому что его `MemUsage` включает page cache, и серверы на
`sendfile`/splice «нагревают» свой cgroup файловыми страницами. Отдельно
замеряются: `idle` — фаза 6 с сразу после `wait_ready()` (пока серверы не
видели нагрузки), `peak` — максимум сэмплов всех wrk-прогонов (интервал 1.5 с).

Фактическая картина (WORKERS=1, Ubuntu 24.04, ядро 7.0):

| Контейнер | idle RSS | idle usg | peak RSS | peak usg | peak cache |
|---|---|---|---|---|---|
| sparrow http | 127 МБ | 133 МБ | 127 МБ | 135 МБ | 0 МБ |
| sparrow tls | 127 МБ | 138 МБ | 129 МБ | 141 МБ | 5 МБ |
| caddy | 11 МБ | 48 МБ | 28 МБ | 66 МБ | 35 МБ |
| nginx | 6 МБ | 16 МБ | 6 МБ | 17 МБ | 8 МБ |

Ключевое отличие sparrow: вся память (пул соединений 10k × буферы 8 КБ,
512 splice-пайпов, 256 × 128 КБ TLS-large-буферов) выделяется **один раз при
старте**, а TLS-контексты создаются лениво на каждое соединение — `idle ≈ peak`
(127 МБ http и tls; раньше tls стоил 316 МБ из-за предвыделения контекстов),
при горячем пути нет ни одной аллокации. Остальные серверы растут под нагрузкой
по мере аллокации соединений/буферов (caddy 11→28 МБ); nginx
держит ~6 МБ. `peak cache` у sparrow ≈ 0: файл 10 МБ — общий page cache хоста
(volume `ro` разделяется между контейнерами), cgroup `file` не «нагревается»
(у caddy/nginx sendfile забирает его в свой cgroup).

Исследовательская фаза (`results/memory_conns.png`, idle RSS, workers=1):

| Контейнер (idle RSS, МБ) | 5 000 | 10 000 | 15 000 | 20 000 |
|---|---|---|---|---|
| sparrow http | 63.6 | 126.8 | 190.0 | 210.7 |
| sparrow tls | 63.6 | 126.8 | 190.0 | 210.8 |
| caddy | 11.3 | 11.2 | 11.2 | 11.2 |
| nginx | 4.3 | 6.4 | 8.5 | 10.6 |

Пул соединений преаллоцируется при старте, поэтому sparrow растёт линейно
(~12.6 МБ на 1000 соединений); caddy плоская, nginx почти плоский.

Если Docker API недоступен (нет `docker.sock`) — в CSV падают пустые
`mem_*` колонки, таблица печатает «-», продолжается со старым `rss_mb`.

## Воркеры (справедливость по CPU)

Один и тот же прогон делается для `WORKERS=1` и `WORKERS=3` (задаётся `--workers "1 3"`):

- sparrow: `worker_threads` (SO_REUSEPORT)
- caddy: `GOMAXPROCS`
- nginx: `worker_processes`

Runner пересоздаёт сервисы через `docker compose up --force-recreate` (docker.sock
смонтирован в runner). **Образы серверов собираются на хосте** (`make bench`):
изнутри runner'а build-контекст резолвится от корня контейнера, поэтому
`run_bench.py` вызывает compose с `--no-build`.

## Ограничения sparrow в бенчмарке

- Upstream-бэкенд задаётся **IPv4-литералом** (sparrow резолвит через `inet_pton`,
  без DNS) — поэтому backend'у выдан статический адрес `172.30.0.10` в compose.
- Встроенный `/big`-хендлер ограничен буфером (~1.7 КБ), поэтому gzip-сценарий
  идёт через `/static/mid.txt` (1.3 КБ) — gzip-путь, доступный всем серверам.
- Для `SEND_ZC` нужны `memlock=-1` и `seccomp=unconfined` — уже в compose.
- Пул 512 splice-пайпов = 1024 fd на воркер: без `nofile: 1048576` в ulimits
  контейнер (дефолт у docker-демона бывает 1024) не стартует — `bind failed:
  Bad file descriptor`. Уже выставлено для sparrow и sparrow-tls.
- Ядро урезает пайпы до 8 КБ, когда пользователь переваливает
  `fs.pipe-user-pages-soft` (16384 страниц ≈ 64 МБ; 512 пайпов = 8192 страницы,
  двух sparrow-серверов + демонов уже хватает). На урезанных пайпах сервер
  калибрует чанк по реальной ёмкости (`F_GETPIPE_SZ` в пуле), но для скорости
  нужны полноразмерные пайпы: `cap_add: SYS_RESOURCE` в compose запрещает
  урезание. Уже выставлено для sparrow и sparrow-tls.
- `-march=native` в Dockerfile sparrow привязывает образ к CPU хоста.

## Как строился стенд: проблемы и их решения

Хроника граблей, на которые наступили при создании/прогоне стенда, и как они
чинились. Коммиты: `b71ece4` (первый прогон без envoy) и `ae1a4b0` (фаза
«чистый sparrow»).

### 1. Убран Envoy из стенда

- **Проблема**: стенд гонял четвёртый сервер (Envoy) — прогон раздувался, а
  сравнение sparrow vs caddy vs nginx уже давало всю нужную картину.
- **Решение**: полное удаление — сервис из `docker-compose.yml`, каталог
  `configs/envoy/`, упоминания в `servers.py`, `run_bench.py`, `summary.py`,
  `run.sh`, backend и всех README.
- **Влияние на бенч**: прогон стал короче (~на треть); цифры sparrow/caddy/nginx
  не изменились — envoy не влиял на остальных.

### 2. snap-docker 29.6.1: `docker compose exec` молча возвращает 1

- **Симптом**: `./run.sh > log.txt` даёт пустой лог и exit code 1, хотя вручную
  каждая команда работает.
- **Диагноз**: в journalctl — `exec attach failed: broken pipe`; эксперимент
  подтвердил: при редиректе stdout `exec`'а в обычный файл демон рвёт
  соединение (баг snap-сборки docker); через терминал или pipe всё работает.
- **Решение**: в `run.sh` и `run_only_sparrow.sh` вывод exec гонится через
  `2>&1 | cat`, а код возврата берётся из `PIPESTATUS[0]`; в README —
  предупреждение: `./run.sh | tee log.txt`, а НЕ `./run.sh > log.txt`.
- **Влияние на бенч**: exit code стал честным (0/1), лог полным; без этого
  `run.sh && echo PASS` мог ложно падать.

### 3. io_uring: entries кольца > 32768 → EINVAL (крах при max_connections > 16384)

- **Симптом**: research-фаза с `max_connections=20000` — sparrow падает.
- **Причина**: ядро ограничивает размер кольца io_uring (32768 entries);
  ring аллоцировался с запасом от `max_connections`.
- **Решение**: кап entries в `src/server.cpp` (entries = min(требуемое, 32768)).
- **Влияние на бенч**: research 5k/10k/15k/20k заработал; при 20k sparrow
  держит 210.7 МБ idle RSS — память растёт линейно с пулом соединений.

### 4. Гонки при пересоздании сервисов (слабые машины)

- **Проблема**: когда `run.sh` поднимал ВСЕ сервисы разом, а runner тут же
  пересоздавал их под воркеры — на слабых машинах старты накладывались,
  wait_ready уходил в таймауты.
- **Решение**: `run.sh` поднимает только runner'а; серверные сервисы
  пересоздаёт сам `run_bench.py` под нужные WORKERS/max_connections. Готовность
  runner'а ждём wait-loop'ом (`docker compose exec -T runner true`), готовность
  серверов — `wait_ready()`. Добавлен `ready_with_retry()` — самолечение: при
  таймауте ожидания сервисы пересоздаются ещё раз и ожидание повторяется.

### 5. Разовая «пауза» прогона (транзиентный сбой docker)

- **Симптом**: `./run.sh` «завис» на 35 минут: ни одного сохранённого
  `results.json` (папка `results/` не тронута), при kill сработал trap `down`.
- **Диагноз**: воспроизведение той же команды вручную прошло штатно
  (полная матрица за ~5 мин); повторный запуск через `nohup` — код 0.
  Следов в логах нет. Вывод: разовый сбой docker/compose, не баг кода.
- **Как диагностировать**: mtime `results.json` (сохраняется после каждого
  WORKERS-блока — если не обновляется, прогон встал до первого сохранения),
  `docker compose logs runner`, `docker ps`.
- **Влияние на бенч**: при повторном запуске цифры стабильны (±шум).

### 6. Лимит соединений — в конфиге sparrow, не в wrk

- **Уточнение**: «потолок» соединений задаётся `max_connections` в
  `configs/sparrow/server.conf` и `server-tls.conf` (подставляется из
  `__MAX_CONNECTIONS__`), а wrk лишь создаёт нагрузку.
- **Решение**: в фазе «чистый sparrow» значение лимита пишется в конфиг, а
  sweep-точки с `c > max_connections` помечаются `pool_limit=true` в
  `results.json`/`results.csv` — sparrow по конфигу отклоняет лишние соединения,
  wrk честно считает их в ошибках (это НЕ провал прогона). В ASCII-сводке —
  сноска, на графике — метка «потолок пула».

### 7. Фаза «чистый sparrow» — отдельный скрипт `run_only_sparrow.sh`

- **Требование**: `run.sh` не трогать; анализ только sparrow — отдельной
  командой, результаты — в отдельную папку (не затирать сравнительные).
- **Решение**: `run_bench.py` получил `--only-sparrow` (сравнительная матрица и
  research пропускаются), `--sparrow-conns "1000 5000"` (по умолчанию пусто —
  в обычном `run.sh` фаза не запускается) и `--no-sparrow`. Семь функций
  (`compose_up`, `wait_ready`/`ready_with_retry`, `sanity_checks`, `bench_one`,
  `measure_idle_memory`, `memory_section`, `run_matrix`) параметризованы
  списками серверов/контейнеров — фаза гоняет матрицу только на sparrow, а
  caddy/nginx останавливаются (`compose stop`) и возвращаются сами при
  следующем полном прогоне.
- **Отдельная папка результатов**: `results-sparrow/` смонтирована в runner
  (одна строка в compose), скрипт передаёт `RESULTS_DIR=/results-sparrow` через
  `docker compose exec -e`; папка создаётся на хосте заранее от имени
  пользователя (иначе docker создал бы её от root, и git add потребовал бы sudo).
- В CSV добавлена колонка `phase` (matrix / research / sparrow).

### 8. Как менялись цифры бенча

Оба прогона — демо-режим (6 с на сценарий, WORKERS=1 и 3), эта же машина.
Первый — `b71ece4` (15:11), второй — `ae1a4b0` (17:16):

| Сценарий | b71ece4 | ae1a4b0 | Δ |
|---|---|---|---|
| W=1 status, sparrow | 195 659 | 180 678 | −8% |
| W=1 status, caddy | 50 222 | 50 324 | ±0% |
| W=1 status, nginx | 94 514 | 97 303 | +3% |
| W=1 TLS, sparrow | 112 868 | 119 802 | +6% |
| W=1 static_big, sparrow | 984 | 1 053 | +7% |
| W=1 static_big, nginx | 1 379 | 1 262 | −8% |
| W=3 status, sparrow | 199 686 | 181 976 | −9% |
| W=3 status, caddy | 142 664 | 113 147 | −21% |
| W=3 status, nginx | 100 345 | 90 368 | −10% |
| W=3 TLS, sparrow | 116 778 | 114 734 | −2% |
| W=3 TLS, caddy | 126 008 | 103 873 | −18% |
| sweep c=1024 (W=1), sparrow | 183 266 | 166 135 | −9% |
| память: caddy peak usage | 66 МБ | 58 МБ | −12% |
| память: sparrow tls peak usage | 141 МБ | 136 МБ | −4% |

Разброс ±10% (caddy на W=3 — до −21%) — это шум демо-режима: короткие
длительности (6 с), параллельная нагрузка хоста (в момент второго прогона
свободно было ~7 ГБ из 15, работали посторонние процессы). **Тренды стабильны**:
sparrow лидирует на status/TLS/gzip и в sweep, nginx — на no-keep-alive и
статике, proxy-сценарии у всех упираются в Python-бэкенд. Для воспроизводимых
цифр есть `--full` (15 с на сценарий) — разброс между прогонами меньше.

Новая фаза «чистый sparrow» (впервые в `ae1a4b0`, демо-режим): status
165 156 / 158 246 rps, TLS 98 391 / 99 715, idle anon RSS 13.1 / 63.8 МБ при
max_connections 1000 / 5000; потолок пула — sweep c=1024 при max=1000 даёт
149 808 rps (против ~157–161k на c≤256), сервер отказывает лишним соединениям,
но не падает. Полная таблица — в разделе «Фаза "чистый sparrow"» выше.
